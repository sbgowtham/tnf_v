The Physics of Bad Data

Time, Space, and Consistency in Distributed Systems

It's month-end close. The finance team's reconciliation report is off by four paise on a total in the crores — not four rupees, four paise. Someone reruns the query. It matches perfectly. An hour later, on the same unchanged data, they run it again. It's off, by a different four paise this time. Nobody touched the database. Nothing failed. The number just isn't stable, and it's never off by enough for anyone but the analyst who now can't let it go.

This is not a rare bug. It's one of about twenty, and every one of them comes from the same place: a single-machine mental model meeting a system that's distributed across time, space, and consistency guarantees that only resolve eventually. A primary key that duplicates itself. A COUNT(*) that changes with no writes. A join on two identical-looking strings that matches nothing. Engineers tend to file these away as one-off horror stories — but they aren't random. They're as predictable as physics, once you know which force is acting on the data.

Twenty of them, with the fix for each.

Part I
Time
01

The primary key that duplicated itself

A key built from local wall-clock time — YYYYMMDDHHMMSS plus a sequence, or a natural key derived from a local date and hour — looks unimpeachably unique. Then, roughly once a year, two genuinely different events land on the same key, and whoever built the schema is certain that's impossible.

It's not impossible, it's daylight saving time. During the fall-back transition, the local clock repeats an hour — 1:00 a.m. to 2:00 a.m. happens twice in the same calendar day — so two real, separate events both get timestamped into that hour and can generate the identical key. UTC-based schemes (Snowflake IDs and similar) never see this, because UTC has no daylight saving. It's specifically legacy ERP systems, telecom billing, and batch jobs built around local business time that get bitten.

The fix is to generate and store every key and timestamp in UTC, and convert to local time only at the point of display. If a local-time key is genuinely unavoidable, bake the UTC offset into the key itself so the repeated hour becomes two distinct values. And don't just trust the generator — add an explicit uniqueness assertion somewhere in the pipeline, so if this ever happens it fails loudly instead of quietly overwriting one event with another.

02

The event that arrived before it was created

A monitoring dashboard shows negative latency — received_at earlier than created_at, which shouldn't be possible for the same event, and yet there it is, in production, on real traffic.

The cause is clock skew between services. Service A's system clock runs a few hundred milliseconds ahead of Service B's — not from a fault, just from ordinary drift that every fleet of machines accumulates. The ugly metric is the visible symptom; the expensive part is invisible: any "keep the latest record" deduplication logic that compares wall-clock timestamps across those two services will silently keep the older version of a record, because the skew reordered which one looked newer.

The fix is to never order events across machines by wall-clock time. Use a broker-assigned sequence — Kafka offsets are the common case — a monotonic version column, or a logical clock instead. Enforce NTP properly and alert when drift exceeds a threshold. And rather than hiding the negative-latency readings, clamp them and count them: a rising count of clamped negative latencies is a live skew monitor you get for free.

03

The day that gained or lost revenue

Daily totals are a few hours off from the source system — consistently, reproducibly — but the monthly total ties out exactly. Whatever's wrong, it isn't data loss.

It's timezone-naive bucketing. The warehouse groups rows by UTC date; the business defines "a day" in local time; and every transaction between local midnight and the UTC offset lands in whichever day the warehouse's clock says it is, not the day the business would say it is. A company operating across several timezones doesn't have one answer to "which day is it" — it has one per region, all valid, all different.

The fix is to store timestamps as timestamp with time zone, or UTC alongside an explicit source-timezone column, and to define exactly one business calendar and one canonical reporting timezone as a documented, queryable dimension table — not as a convention everyone is supposed to remember. Bucket every report against that dimension table, never against the raw timestamp directly.

04

The row that arrived after the door closed

A dashboard number for yesterday quietly changes three weeks from now — or it doesn't, and stays wrong forever, because nobody was watching that number closely enough to notice.

The cause is late-arriving data landing in a partition the pipeline already considered finished. Mobile clients buffer events offline for days before they get a signal. Upstream systems occasionally replay a batch. The nightly job scanned that day's partition on schedule, produced its output, and moved on — it has no reason to look at that partition again, and nothing tells it to.

The fix is to partition storage by ingestion time but query by event time, or maintain an explicit watermark plus a rolling reprocessing window — re-running the last several days every night rather than assuming yesterday is final the moment it's been processed once. Track event-time-to-ingestion-time lag as its own chart, so the size of that window is set from evidence about how late data actually arrives, not from a guess.

Part II
Space
05

The COUNT(*) that changed with no writes

Run SELECT COUNT(*) FROM orders twice, ten seconds apart. No ETL job is running. Nobody on the team is writing to the table. And the two numbers are different — not close, different, on a table nobody touched.

From the analyst's seat, it's "the same table, queried twice." Physically, it's several copies of the table converging asymmetrically. A load balancer routed the first query to one read replica and the second to another, and each replica sits at a slightly different point in the replication stream from the primary. Neither answer is wrong. They're both correct answers to a question that has a different answer depending on which physical machine you asked.

The fix is to pin reconciliation and reporting queries to the primary, or to one designated replica, rather than letting a load balancer route them wherever. Expose replication lag as a first-class metric next to whatever dashboard shows this number. And for anything that needs to be auditable — financial reporting, compliance exports — read from a versioned snapshot with snapshot isolation rather than from "the current table," because "current" is a moving target with more than one simultaneous value.

06

The write that vanished right after you made it

An insert succeeds. The service immediately reads the row back to confirm it, and gets nothing. A moment later, the same read returns the row, correctly.

This is read-after-write inconsistency against an asynchronous replica, and it shows up most often right after a failover — the new primary is momentarily behind what a client just wrote through the old one, or a read got routed to a replica that hasn't caught up yet.

The fix is to route any read-your-own-write path to the primary, or to use session or monotonic consistency if the engine offers it, rather than a generic load-balanced read. And avoid building orchestration logic that writes and then immediately polls a replica to confirm the write happened — that pattern is exactly what surfaces this failure mode, and it will eventually surface it in production, where replication lag is never as close to zero as it is in a test environment.

07

The file that isn't in the listing

A job writes 500 files to object storage. The downstream job lists the same location and processes 497. No error, anywhere — the missing three simply weren't in the listing when the downstream job asked.

It's tempting to blame "S3 is eventually consistent" — but as of December 2020, S3 provides strong read-after-write consistency automatically, for both individual objects and listings, so that specific historical cause is largely retired for S3 itself. What's left is more fundamental: object storage has no concept of a multi-file transaction. A writer producing 500 files performs 500 independent operations, and a reader is free to list the bucket at any point during that sequence — including the exact moment when 497 have landed and 3 haven't. Every object is individually consistent; the batch of 500, as a batch, has no atomicity guarantee at all. Table formats without strict commit semantics inherit exactly this gap.

The fix is to stop discovering work by listing a prefix and hoping it's complete. Have the writer emit an explicit manifest of exactly what it produced, and have every reader consume that manifest instead of the directory. Or adopt a table format with atomic commits — Iceberg, Delta, Hudi — so a reader sees either the full, consistent snapshot or nothing, never a partial one.

08

The row that exists but no query finds it

SELECT * on the whole table finds the row. Every dated or filtered query misses it. The row counts and the row sums have disagreed for weeks, by exactly one row's worth, and nobody can find where.

The row's partition key was updated after the row was written, so it physically moved to a different partition — or it landed outside whatever range the queries scan. Partition pruning is doing exactly what it's designed to do: skip partitions the query planner is confident don't matter. It's just confident about the wrong thing, because the assumption that a partition key never changes turned out not to hold.

The fix is to treat partition keys as immutable in practice — delete and re-insert the row rather than updating the key that determines its physical location. And run a periodic reconciliation that compares an unpartitioned total against the sum of every partition's total; a gap that persists across runs is the alarm, long before a human notices the row is "missing."

09

The update that lost to an older update

A correction is applied to a customer record. It's confirmed on screen. A few minutes later, it's gone — silently reverted to the value it had before the correction, with no error logged anywhere.

This is multi-region or multi-master replication resolving a write conflict by last-write-wins, using wall-clock timestamps to decide which write is "newer." If the machine that applied the correction had a clock running even slightly behind the machine that made the original write, the correction loses the tiebreak — the system is certain, by its own logic, that the older write happened later.

The fix is to resolve conflicts with version vectors, monotonic revision numbers, or a CRDT, never with wall-clock timestamps. Where the business can tolerate it, route all writes for a given entity to a single region so there's no conflict to resolve in the first place. And whatever resolution strategy is in place, log every conflict resolution explicitly — a loss that's visible in a log is a bug; a loss that isn't logged at all is the one that costs someone their afternoon three months later trying to explain a customer complaint.

10

The dimension that changed under a running join

A report joins a fact table to a dimension table and produces a total that matches neither source system — and running the exact same query again produces a different, still-wrong total.

The two tables were read at different moments within the same job, and the dimension changed in the gap between them — a customer's region got updated mid-run, so the first half of the join used the old region and the second half used the new one, blending two versions of a fact that was only ever supposed to have one.

The fix is to read every input to a job from one consistent point in time — a single transaction, or explicitly pinned table versions — rather than letting each table be read whenever the query planner gets around to it. For dimensions specifically, model them as slowly changing with validity date ranges, and join on the fact's effective date against that range, rather than against whatever the dimension's current state happens to be at query time.

Part III
Consistency and Determinism
11

The SUM() that returns a different total each run

Finance flags a reconciliation break of a few paise. Someone reruns the exact same query on the exact same unchanged data. It matches. They run it again the next morning. It's off — by a different few paise than the first time.

Floating-point addition isn't associative — (a + b) + c doesn't always equal a + (b + c) once rounding is involved — and a parallel query engine is free to partition the data differently on every run and add the partial sums in a different order each time. Trailing decimal places drift as a direct result. Nobody wrote a bug; IEEE 754 floating-point arithmetic is behaving exactly as specified, and the specification never promised identical results under arbitrary reordering.

The fix is to store money as DECIMAL or NUMERIC, never FLOAT or DOUBLE, so the arithmetic is exact rather than approximate. Where floats genuinely can't be avoided, round to a defined precision before any comparison, and give reconciliation checks an explicit tolerance instead of expecting bit-for-bit equality the data type was never able to guarantee.

12

The pagination that skips and repeats rows

An export pages through 100,000 rows, 1,000 at a time. The total row count at the end matches. The contents don't — some rows appear on two different pages, and others don't appear on any page at all.

ORDER BY on a column that isn't unique, combined with LIMIT/OFFSET, has no way to guarantee a stable order for rows that tie on the sort value. The database is free to order those tied rows differently on each page request, and if a tied row crosses the boundary between two pages, it can land on both, or on neither, depending on how the tie resolved that time.

The fix is to always add a unique column as a tiebreaker to the sort key. Better still, paginate by keyset instead of offset: WHERE (sort_col, id) > (last_sort, last_id), which is both correct and faster on large tables than OFFSET, which has to scan and discard every row before the requested page.

13

The GROUP BY that picks a value at random

A grouped query returns a plausible-looking value in a non-aggregated column, and it's a different plausible value every time the query runs.

The column was selected without being wrapped in an aggregate function and without appearing in the GROUP BY clause. Some engines reject this outright as a syntax error. Others silently pick one arbitrary row from each group to source that column's value from, and don't tell you which row, or that a choice was even made.

The fix is to enable the engine's strict mode — ONLY_FULL_GROUP_BY in MySQL, or the equivalent elsewhere — so this becomes a hard error instead of a silent guess. Where a specific row's value genuinely is what's wanted, say so explicitly: MIN(), MAX(), or a windowed ROW_NUMBER() over an explicit ordering, so the choice of which row wins is a decision in the query, not an implementation detail of the engine.

14

The backfill that didn't match the original run

A historical job gets rerun for a past date window, to fix a bug that affected that period. The rerun produces different output than the original run did for that same window — which defeats the entire point of being able to rerun it.

Somewhere in the transformation logic sits a non-deterministic function — CURRENT_TIMESTAMP, NOW(), RAND(), CURRENT_USER — or a view that reads whatever "today's" state of some table happens to be, rather than the state as it existed on the date being processed. The original run and the backfill execute at genuinely different points in time, so anything that implicitly depends on "now" gets a different answer each time, even though the input data for that historical window is identical.

The fix is to pass the logical execution date into the job as an explicit parameter and use it everywhere the logic needs "the current date" — never NOW(). Ban non-deterministic functions from transformation logic outright and enforce that with code review or a linter, not a style guide nobody reads. A job should be a pure function of its input snapshot and its execution date — nothing else.

15

The retry that double-counted revenue

Daily revenue totals are correct, day after day — except on the days when some task in the pipeline failed partway through and got automatically retried, and on those days the total is inflated by roughly what that task processes.

The step that failed wasn't idempotent. It appended rows as part of its work, failed further along in the same run, and the retry started over from the beginning and appended the same rows a second time. The orchestrator sees a failed attempt followed by a successful one and reports the whole thing as a success — which, from its point of view, it was.

The fix is to make every write in the pipeline idempotent by construction: MERGE or upsert on a business key, or delete-the-partition-then-insert, rather than blind append. Use atomic commits so a partial write from a failed attempt is never visible to a downstream reader in the first place. And where the pipeline calls an external API, carry an idempotency key through that call too — the failure mode is identical whether the duplicate write happens inside the warehouse or on the other side of a network call.

Part IV
Identity
16

The ID that was issued twice

Two completely unrelated orders, placed months apart, share the same order ID — and the database's uniqueness constraint on that column is still in place, still valid, and was never violated at the moment either row was inserted.

There are two distinct ways this happens, and it matters which one is in play. In MySQL 5.7 and earlier, InnoDB kept the auto-increment counter only in memory; after a restart, it recomputed the counter as MAX(id) + 1 by scanning the table, and if the row holding that maximum id had since been deleted, the same id got issued again to a new row. MySQL 8.0 fixed this specific case by persisting the counter through the redo log. The other cause is unrelated to that fix and still very much alive today: a replica gets promoted to primary during a failover before it has fully replicated the old primary's latest sequence state, and the newly promoted primary resumes handing out IDs starting from a point the old primary had already passed. The database's uniqueness guarantee was always real — it was just scoped to one node, for one lifetime of that node, and a restart or a failover is exactly the kind of event that ends a lifetime.

The fix is to use UUIDv4/v7 or a coordinated ID-generation service for any identifier that has to leave the database it was born in. Never treat a source system's auto-increment ID as globally unique once it reaches a warehouse: key on (source_system, source_id, load_date) instead, and add a hard duplicate check at ingestion regardless of which database generated the original ID.

17

The unique constraint that allowed duplicates

Twelve rows exist for the same customer, in a table with a UNIQUE(customer_id, region_code) constraint that has never been dropped, disabled, or violated according to the database.

NULL is not equal to NULL in the vast majority of SQL engines — including inside a unique constraint's own logic. UNIQUE(customer_id, region_code) prevents two rows with the same customer_id and the same non-NULL region_code. It does nothing at all to stop any number of rows with the same customer_id and a NULL region_code, because by the engine's own rules, no two NULLs are ever "the same value" to compare.

The fix is to make every column inside a unique key NOT NULL, using an explicit sentinel value — 'UNKNOWN', or a reserved code — to represent "we don't know the region" instead of leaving it absent. Where the engine supports expression or partial indexes, a unique index over COALESCE(region_code, sentinel) achieves the same result without changing what NULL means everywhere else in the table.

18

The hash key with real collisions

A surrogate key built from MD5(concat(col_a, col_b)) is supposed to be collision-proof for all practical purposes, and yet two clearly different pairs of input values are producing the identical hash far too often to be a genuine cryptographic collision.

It isn't a hash collision. It's string concatenation with no delimiter: the pair ('AB', 'C') and the pair ('A', 'BC') concatenate to the identical string 'ABC' before the hash function ever runs, and MD5 correctly, faithfully produces the same hash for the same string. The hash function did its job perfectly; the bug arrived one step earlier, wearing the hash's costume.

The fix is to concatenate with a delimiter that provably cannot appear inside the data itself, and to represent NULL values explicitly in that concatenation rather than silently as an empty string, which just reintroduces the same ambiguity. Normalise casing and whitespace trimming before hashing, not after — applied inconsistently, the same logical value produces two different keys depending on which step happened first.

19

The upsert that merged two people

There's no duplicate row this time — the opposite happens. Two entirely different customers collapse into a single record with their histories blended together, and no error fires anywhere in the pipeline, because as far as the merge logic is concerned, nothing went wrong.

The merge key was LOWER(TRIM(email)). That's a reasonable-looking normalization rule until two different people at the same company both use info@acme.com — a shared team inbox, not a personal identifier — and the merge treats them as one person because their normalized email is identical. A subtler version of the same failure comes from case-folding rules themselves: some collations treat certain distinct characters as equal under casing rules (the Turkish dotless ı against a regular i is the textbook example), so two genuinely different strings normalize to the same value and trigger a merge that never should have happened.

The fix is to merge on a key that's actually meant to identify a person — not on a contact attribute like email that can legitimately be shared, reused, or reassigned. Where fuzzy matching is genuinely required, route candidate matches to a human review queue instead of applying them automatically and silently. And keep the pre-merge rows around after any merge, so the merge is a reversible operation rather than a one-way door — because eventually, one of these merges will need to be undone, and "we don't have the original rows anymore" is the point where that becomes impossible instead of just annoying.

Part V
Encoding and Types
20

The join that matched nothing, and the column that became null

Two values look completely identical on screen — same font, same characters, same everything a human can see — and a join between them matches zero rows. Somewhere else in the same pipeline, every row for one particular country has quietly vanished from a report, replaced by nulls.

These are two separate failures with the same root cause: the data changed in transit, invisibly. The join failure is usually Unicode normalization — "José" stored with a single precomposed é character in one system (NFC) and stored as a plain e plus a separate combining accent mark in another (NFD). Byte-for-byte different, pixel-for-pixel identical on screen, and a string comparison sees two different strings. Non-breaking spaces pasted in from a web form, trailing whitespace, and zero-width characters cause the identical symptom through the identical mechanism.

The vanishing country is a type-inference failure: the ISO country code NA — Namibia — gets read by a default CSV parser as the string "not available" and silently converted to NaN, deleting a real country's data because its code looks like a null marker. The same family of bug strips leading zeros from postcodes and account numbers, coerces IDs like 1.23E5 into floating-point numbers, and — the well-known one — converts gene names that look like dates into actual dates inside a spreadsheet.

The fix is to normalize all incoming text to NFC and explicitly strip invisible characters at the point of ingestion, not downstream where the damage is already several joins deep. Never rely on inferred schemas at a system boundary: declare every column's type explicitly, read identifiers as strings rather than numbers, and set the null sentinel deliberately (keep_default_na=False and its equivalents) instead of trusting a parser's defaults. A contract test that fails the moment an inferred type changes catches this category of bug before it reaches anyone's dashboard.

The pattern underneath all twenty is the same one: each is impossible in a mental model built around one clock, one machine, and one authoritative copy of the data. Production has none of those three things, on any system large enough to need more than one server. Once that stops being a surprise, these twenty stop being ghost stories that happen to you, and start being a checklist you run before they do.
